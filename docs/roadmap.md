# Roadmap — верхнеуровневые задачи

Статус: оркестрация (типы + `certificateAuthFlow.ts`) и привязка к плагину
(`WindowCadesPluginAdapter`) реализованы, покрыты тестами (мок `window.cadesplugin`) и проверены
2026-09-25 на реальном стенде (настоящий плагин, реальное хранилище сертификатов, реальный
GOST-сертификат) — см. открытый вопрос 1, ныне закрытый.

## Зачем эта библиотека вообще нужна

Полная схема аутентификации по ЭП для Контур.ОФД (см. `relsy/backend/docs/ofd-receipts-design.md`,
§3, worktree `relsy-ofd-receipts`) — пять шагов, из них два сетевых (backend → Контур.ОФД, уже
покрыты `kontur-ofd-php-sdk`'s `AuthClient::authenticateByCert()`/`approveCert()`), два —
браузер↔свой backend (специфичны для конкретного приложения-потребителя, не для этой библиотеки), и
один — **браузерная ГОСТ-расшифровка через КриптоПро ЭЦП Browser plug-in**. Вот этот последний шаг
и есть единственная причина существования `kontur-ofd-js-auth`: это не общая работа с ЭП-плагином
(тот сам по себе не про Контур.ОФД), а протокол-специфичная склейка — какую именно операцию плагина
вызвать и в каком виде результат нужен для `approve-cert`, зеркалит на клиенте то же самое знание,
которое `AuthClient` уже воплощает на сервере.

**Эта библиотека не делает сетевых запросов вообще, ни к Контур.ОФД, ни к чьему-либо backend** —
`api.kontur.ru` не отдаёт CORS-заголовков ни на одном эндпоинте (проверено эмпирически 2026-09-24,
см. `ofd-receipts-design.md` §3), так что вызывать его напрямую из браузера физически нельзя; вызовы
к собственному backend потребителя (`.../certificate-frontend/init`, `.../certificate-frontend/
approve`) — забота потребителя, не этой библиотеки (у каждого приложения свой контракт, свои
эндпоинты, своя авторизация).

## ~~Оркестрация~~ — реализовано

- `CryptoProAdapter` — интерфейс, описывающий, что нужно ОТ плагина (список сертификатов, экспорт
  в Base64, расшифровка блоба) — сама библиотека им не владеет, только зависит от него. Позволяет
  тестировать `certificateAuthFlow.ts` без реального плагина/браузера.
- `getCertificateForInit(adapter, thumbprint)` — сертификат в Base64 для шага
  `.../certificate-frontend/init`.
- `decryptForApproveCert(adapter, encryptedKey)` — расшифровывает `EncryptedKeyResponse` через
  адаптер, собирает `ApproveCertPayload` для шага `.../certificate-frontend/approve`. **Без
  отпечатка сертификата** — в отличие от первой версии этого документа, реальный API расшифровки
  (`CAdESCOM.CPEnvelopedData.Decrypt()`, см. открытый вопрос 1) не принимает сертификат как
  параметр вообще, ищет подходящий приватный ключ в хранилище сам по содержимому CMS-конверта.
  Ничего не сохраняет и не кэширует — оба байтовых значения (зашифрованное и расшифрованное) живут
  только на время одного вызова.
- Обе функции проверяют непустоту строк на входе/выходе (та же дисциплина, что
  `AuthClient::requireString()` в `kontur-ofd-php-sdk`) — не пропускать молча пустую строку туда,
  где дальше по цепочке будет либо криптооперация, либо HTTP-запрос с бессмысленным телом.

## ~~Привязка к плагину~~ — реализовано, не проверено на реальном стенде

`WindowCadesPluginAdapter` — собрано и сверено против официальной документации CryptoPro
(`docs.cryptopro.ru/cades/plugin/*`, `docs.cryptopro.ru/cades/reference/cadescom/*`),
`cadesplugin_api.js` (v2.4.5) и демо-примера `async_code.js` с cryptopro.ru — не по памяти и не по
обрывочным сведениям, каждый вызов подтверждён источником:

- `window.cadesplugin` — сам нативный `Promise`, `await` его напрямую; резолвится с `undefined` —
  после ожидания используется сам объект `cadesplugin`, не результат `await` (частая ловушка: если
  вернуть `cadesplugin` из async-функции как есть, рантайм схлопнет его через thenable-chaining до
  `undefined` — TypeScript поймал это на этапе тайпчека, см. `getCadesplugin()` в
  `WindowCadesPluginAdapter.ts`, возвращает `{ plugin }`, не `plugin` напрямую).
- Сертификаты — `CAdESCOM.Store` → `.Open(CAPICOM_CURRENT_USER_STORE=2, CAPICOM_MY_STORE="My",
  CAPICOM_STORE_OPEN_MAXIMUM_ALLOWED=2)` → `.Certificates` (`.Count`/`.Item(i)`, индексация с 1) →
  `.Thumbprint`/`.Export(CADESCOM_ENCODE_BASE64)` (не `CAPICOM_ENCODE_BASE64` — той константы в
  `cadesplugin_api.js` нет).
- Расшифровка — `CAdESCOM.CPEnvelopedData` (не `CAdESCOM.EnvelopedData`, как предполагалось в
  первой версии этого документа — такого класса нет в официальном списке объектов CAdESCOM):
  `propset_ContentEncoding(CADESCOM_BASE64_TO_BINARY)` **до** `Decrypt()`, иначе `Content` придёт
  UCS2LE-строкой, а не Base64 байт; `Decrypt(cmsBase64)` ничего не возвращает, результат — в
  `Content` после успешного вызова. Сертификат/отпечаток в `Decrypt()` не передаётся — плагин сам
  находит нужный приватный ключ в хранилище по самому CMS-конверту.
- Фильтрация сертификатов (см. открытый вопрос 2) — `PublicKey` у `CAdESCOM.Certificate` это
  **метод**, не свойство (`await cert.PublicKey()`, не `await cert.PublicKey`); алгоритм —
  `await (await cert.PublicKey()).Algorithm` (объект `Oid`) → `await algorithm.Value` (строка OID).
  ГОСТ Р 34.10 сверяется по точным OID (`1.2.643.2.2.19` — 2001, `1.2.643.7.1.1.1.1` — 2012/256,
  `1.2.643.7.1.1.1.2` — 2012/512; RFC 4491 §2.3.2, RFC 9215 §4.1), не префиксом `1.2.643.` — та же
  ветка содержит и устаревший ключевой OID ГОСТ Р 34.10-94, который не должен молча проходить как
  современный алгоритм. Срок действия — `ValidFromDate`/`ValidToDate` (тип не документирован,
  официальный демо-код оборачивает в `new Date(...)`, так же сделано и здесь) сравниваются вручную,
  а не через `Certificate.IsValid()` — тот строит полную цепочку сертификатов и может обращаться в
  сеть за проверкой отзыва (поведение `CheckFlag` для CryptoPro не задокументировано), что не
  годится для быстрой локальной фильтрации списка. Наличие приватного ключа — `HasPrivateKey()`
  (документированный метод, но проверяет только наличие свойства `CERT_KEY_PROV_INFO_PROP_ID`, не
  что контейнер ключа реально доступен).

## Открытые вопросы

1. ~~`WindowCadesPluginAdapter` не запускался на реальном стенде`~~ — **проверено 2026-09-25** через
   `manual-test/index.html` (см. этот файл, инструкция по запуску — в его комментариях/README) на
   машине с установленным КриптоПро CSP + ЭЦП Browser plug-in и реальным хранилищем сертификатов
   (21 сертификат, включая тестовые ГОСТ-сертификаты пользователя). Подтверждено на реальных
   объектах (не моках):
   - `listCertificateThumbprints()` — открывает `CAdESCOM.Store` (`CAPICOM_CURRENT_USER_STORE`,
     `"My"`) и возвращает реальные отпечатки без ошибок.
   - `getCertificateBase64()` — экспортирует сертификат в Base64 (`CADESCOM_ENCODE_BASE64`),
     результат синтаксически корректен (проверено декодированием).
   - `decryptEncryptedKey()` — **`Decrypt()` действительно находит нужный приватный ключ в
     хранилище сам, без явного указания сертификата**: собрали реальный CMS-конверт
     (`CAdESCOM.CPEnvelopedData.Encrypt()` на подходящем ГОСТ-сертификате) и расшифровали его через
     наш адаптер — round-trip совпал побайтово. Это самый рискованный из непроверенных вызовов, и
     он подтверждён на живых объектах, а не только по документации.

   Что осталось непроверенным (не блокирует использование, но стоит держать в уме):
   код ошибки `0x8009200C` (`CRYPT_E_NO_DECRYPT_CERT`) как единственный код на «нет подходящего
   ключа» — не воспроизводился напрямую (см. другую находку ниже); принимает ли `Decrypt()` Base64
   с переносами строк/PEM-заголовками — тестировался только «чистый» Base64 без переносов, как его
   и будет присылать backend после `AuthClient::authenticateByCert()`; полный путь с реальным
   `EncryptedKey` от Контур.ОФД (а не самодельным CMS-конвертом) — ждёт организационного доступа
   к тестовой площадке (`Endpoints.rst`).

   **Побочная находка**: не каждый сертификат в хранилище пригоден для ГОСТ-шифрования — из 21
   сертификата в тестовом хранилище шифрование (`CPEnvelopedData.Encrypt()`) успешно сработало
   только на части ГОСТ-сертификатов пользователя; RSA-сертификаты (например, Adobe) падают с
   `NTE_BAD_KEY` (`0x80090003`, «Плохой ключ»), часть служебных ГОСТ-сертификатов без ключа
   шифрования падает с `E_INVALIDARG` (`0x80070057`, «Параметр задан неверно»). Это ошибка на
   стороне библиотеки-потребителя не нашей, но напрямую усиливает открытый вопрос 2 ниже: недостаточно
   дать пользователю выбрать любой сертификат из списка, потребитель должен быть готов, что плагин
   отклонит непригодный выбор с этими кодами ошибок и понятно объяснить это пользователю.
2. ~~Выбор сертификата при нескольких на токене~~ — **сужено 2026-09-25**: сам UI выбора (если
   подходящих сертификатов больше одного) по-прежнему забота потребителя, не этой библиотеки — но
   *какие сертификаты вообще предлагать на выбор* решает уже сама библиотека, а не потребитель.
   `listCertificateThumbprints()` теперь молча отфильтровывает сертификаты, непригодные для этого
   шага (не ГОСТ Р 34.10-2001/2012, просрочен/ещё не наступил срок действия, нет приватного ключа в
   хранилище) — то есть в реальном тестовом хранилище из 21 сертификата в список попадут только
   пригодные. `getCertificateBase64(thumbprint)`, в отличие от списка, принимает отпечаток явно (в
   обход UI выбора) — на непригодный сертификат бросает `Error` с перечислением всех причин сразу
   (алгоритм/срок/ключ/PrivateKeyUsagePeriod/KeyUsage), а не молча его пропускает и не подсовывает
   плагину, который откажет собственной невразумительной `NTE_BAD_KEY`/`E_INVALIDARG` ошибкой.

   Две дополнительные проверки добавлены 2026-09-25 (см. `WindowCadesPluginAdapter.ts`):
   `PrivateKeyUsagePeriodFrom`/`PrivateKeyUsagePeriodTo` (OID `2.5.29.16`, необязательное
   расширение — отсутствие/исключение при чтении трактуется как «нет ограничения», так же
   поступает официальный демо-код CryptoPro) и `KeyUsage()` (OID `2.5.29.15` — метод, не свойство;
   требуем `IsKeyEnciphermentEnabled` ИЛИ `IsKeyAgreementEnabled`, когда `IsPresent`, иначе тоже
   «нет ограничения»). **Проверено вживую 2026-09-25** на том же реальном хранилище: у 9 личных
   ГОСТ-сертификатов пользователя `PrivateKeyUsagePeriodTo` оказался реальным отдельным сроком, на
   1 секунду – 10 минут раньше `ValidToDate` — это не гипотетическая, а настоящая независимая
   проверка на этом стенде. У не-ГОСТ/служебных сертификатов чтение `PrivateKeyUsagePeriodTo`
   действительно бросает исключение (`0x80092004`, «Объект или свойство не найдено») — подтверждает
   выбор трактовать исключение как «нет ограничения», а не как непригодность. `KeyUsage()` у всех
   9 личных ГОСТ-сертификатов вернул `IsPresent=true` с `IsKeyEnciphermentEnabled` включённым (ни
   один реальный сертификат в этом хранилище не оказался «только для подписи» — само это условие
   проверено пока только на моках, не на реальном подписывающем-без-шифрования сертификате).
   Наблюдение: сам плагин резолвит `Is*Enabled` числом `0`/`1`, не булевым `false`/`true` — учтено в
   `cadesplugin.types.ts` комментарием, логика `||` от этого не страдает (JS сам приводит типы).

   **Проверено вживую 2026-09-25** (`manual-test/index.html`, кнопки 4-5, реальное хранилище из 21
   сертификата): `listCertificateThumbprints()` действительно вернул только 3 сертификата — ГОСТ
   Р 34.10-2012/256 (`1.2.643.7.1.1.1.1`) с ещё не истёкшим сроком действия; отсеялись и RSA-
   сертификаты (`1.2.840.113549.1.1.1`), и обычные EC-сертификаты не по ГОСТ (`1.2.840.10045.2.1`,
   служебные с CN-UUID), и просроченные ГОСТ-сертификаты того же пользователя (несколько штук,
   формально с тем же алгоритмом, но `ValidToDate` в прошлом — были бы включены без проверки дат).
   `getCertificateBase64()` на конкретных непригодных сертификатах бросил ожидаемые точные
   сообщения: `"...does not use a GOST public-key algorithm..."` для не-ГОСТ сертификата и
   `"...is expired or not yet valid"` отдельно для просроченного ГОСТ-сертификата — оба случая
   различимы, не одна общая ошибка на всё. `decryptEncryptedKey()`
   сертификат не принимает вообще (см. выше) — фильтровать в нём нечего.
