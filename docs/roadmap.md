# Roadmap — верхнеуровневые задачи

Статус: оркестрация (типы + `certificateAuthFlow.ts`) и привязка к плагину
(`WindowCadesPluginAdapter`) реализованы и покрыты тестами (мок `window.cadesplugin`, реальный
плагин не запускался) — см. открытый вопрос 1.

## Зачем эта библиотека вообще нужна

Полная схема аутентификации по ЭП для Контур.ОФД (см. `relsy/backend/docs/ofd-receipts-design.md`,
§3, worktree `relsy-ofd-receipts`) — пять шагов, из них два сетевых (backend → Контур.ОФД, уже
покрыты `kontur-ofd-php-sdk`'s `AuthClient::authenticateByCert()`/`approveCert()`), два —
браузер↔свой backend (специфичны для конкретного приложения-потребителя, не для этой библиотеки), и
один — **браузерная ГОСТ-расшифровка через КриптоПро ЭЦП Browser plug-in**. Вот этот последний шаг
и есть единственная причина существования `kontur-ofd-js-auth`: это не общая работа с ЭП-плагином
(тот сам по себе не про Контур.ОФД), а протокол-специфичная склейка — какую именно операцию плагина
вызвать и в каком виде результат нужен для `approve-cert`, зеркалит на клиенте то же самое знание,
которое `AuthClient` уже воплощает на сервере.

**Эта библиотека не делает сетевых запросов вообще, ни к Контур.ОФД, ни к чьему-либо backend** —
`api.kontur.ru` не отдаёт CORS-заголовков ни на одном эндпоинте (проверено эмпирически 2026-09-24,
см. `ofd-receipts-design.md` §3), так что вызывать его напрямую из браузера физически нельзя; вызовы
к собственному backend потребителя (`.../certificate-frontend/init`, `.../certificate-frontend/
approve`) — забота потребителя, не этой библиотеки (у каждого приложения свой контракт, свои
эндпоинты, своя авторизация).

## ~~Оркестрация~~ — реализовано

- `CryptoProAdapter` — интерфейс, описывающий, что нужно ОТ плагина (список сертификатов, экспорт
  в Base64, расшифровка блоба) — сама библиотека им не владеет, только зависит от него. Позволяет
  тестировать `certificateAuthFlow.ts` без реального плагина/браузера.
- `getCertificateForInit(adapter, thumbprint)` — сертификат в Base64 для шага
  `.../certificate-frontend/init`.
- `decryptForApproveCert(adapter, encryptedKey)` — расшифровывает `EncryptedKeyResponse` через
  адаптер, собирает `ApproveCertPayload` для шага `.../certificate-frontend/approve`. **Без
  отпечатка сертификата** — в отличие от первой версии этого документа, реальный API расшифровки
  (`CAdESCOM.CPEnvelopedData.Decrypt()`, см. открытый вопрос 1) не принимает сертификат как
  параметр вообще, ищет подходящий приватный ключ в хранилище сам по содержимому CMS-конверта.
  Ничего не сохраняет и не кэширует — оба байтовых значения (зашифрованное и расшифрованное) живут
  только на время одного вызова.
- Обе функции проверяют непустоту строк на входе/выходе (та же дисциплина, что
  `AuthClient::requireString()` в `kontur-ofd-php-sdk`) — не пропускать молча пустую строку туда,
  где дальше по цепочке будет либо криптооперация, либо HTTP-запрос с бессмысленным телом.

## ~~Привязка к плагину~~ — реализовано, не проверено на реальном стенде

`WindowCadesPluginAdapter` — собрано и сверено против официальной документации CryptoPro
(`docs.cryptopro.ru/cades/plugin/*`, `docs.cryptopro.ru/cades/reference/cadescom/*`),
`cadesplugin_api.js` (v2.4.5) и демо-примера `async_code.js` с cryptopro.ru — не по памяти и не по
обрывочным сведениям, каждый вызов подтверждён источником:

- `window.cadesplugin` — сам нативный `Promise`, `await` его напрямую; резолвится с `undefined` —
  после ожидания используется сам объект `cadesplugin`, не результат `await` (частая ловушка: если
  вернуть `cadesplugin` из async-функции как есть, рантайм схлопнет его через thenable-chaining до
  `undefined` — TypeScript поймал это на этапе тайпчека, см. `getCadesplugin()` в
  `WindowCadesPluginAdapter.ts`, возвращает `{ plugin }`, не `plugin` напрямую).
- Сертификаты — `CAdESCOM.Store` → `.Open(CAPICOM_CURRENT_USER_STORE=2, CAPICOM_MY_STORE="My",
  CAPICOM_STORE_OPEN_MAXIMUM_ALLOWED=2)` → `.Certificates` (`.Count`/`.Item(i)`, индексация с 1) →
  `.Thumbprint`/`.Export(CADESCOM_ENCODE_BASE64)` (не `CAPICOM_ENCODE_BASE64` — той константы в
  `cadesplugin_api.js` нет).
- Расшифровка — `CAdESCOM.CPEnvelopedData` (не `CAdESCOM.EnvelopedData`, как предполагалось в
  первой версии этого документа — такого класса нет в официальном списке объектов CAdESCOM):
  `propset_ContentEncoding(CADESCOM_BASE64_TO_BINARY)` **до** `Decrypt()`, иначе `Content` придёт
  UCS2LE-строкой, а не Base64 байт; `Decrypt(cmsBase64)` ничего не возвращает, результат — в
  `Content` после успешного вызова. Сертификат/отпечаток в `Decrypt()` не передаётся — плагин сам
  находит нужный приватный ключ в хранилище по самому CMS-конверту.

## Открытые вопросы

1. **`WindowCadesPluginAdapter` не запускался на реальном стенде** с настоящим плагином, токеном и
   `EncryptedKey` от Контур.ОФД — только против официальной документации и с моком `window.
   cadesplugin` в тестах. Не подтверждено (см. исследование, зафиксированное в этом коммите):
   находит ли `Decrypt()` сертификаты, лежащие только в контейнере (`CADESCOM_CONTAINER_STORE`), а
   не установленные в хранилище; код ошибки `0x8009200C` (`CRYPT_E_NO_DECRYPT_CERT`) — что это
   единственный код на «нет подходящего ключа»; принимает ли `Decrypt()` Base64 с переносами строк/
   PEM-заголовками (сейчас передаём как есть — `getCertificateBase64()` результат `Export()` чистит
   от пробелов, `decryptEncryptedKey()` входной `encryptedKeyBase64` — нет, он приходит от backend,
   который сам получил его от Контур.ОФД). Пройти весь путь на тестовой площадке (`Endpoints.rst`,
   бесплатный доступ) до первого реального использования.
2. **Выбор сертификата при нескольких на токене** — `listCertificateThumbprints()` в контракте
   есть, но сам UI выбора (если сертификатов больше одного) — забота потребителя (React/Angular/
   что угодно), не этой библиотеки; здесь только фиксирую, что контракт это не блокирует.
3. **Упаковка/публикация** — публиковать ли в npm под `@dudev/kontur-ofd-js-auth`, или пока
   достаточно git-зависимости (`"kontur-ofd-js-auth": "github:dudev/kontur-ofd-js-auth"` в
   `package.json` потребителя) — как `kontur-ofd-php-sdk` до появления второго потребителя. Решить,
   когда появится первый реальный consumer (relsy frontend, `admin/ofd-auth/*`).
